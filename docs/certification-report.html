Production Readiness Certification

Plateau State Grassroots Revenue Platform

An independent assessment of whether this application can safely be trusted with real government revenue and real taxpayer information — conducted by driving the running system against a live PostgreSQL database and attacking its stated guarantees from outside.

Not production ready

The application logic is sound. The system around it does not yet exist.

Every financial invariant this platform claims survived direct attack, including attacks that bypass the application entirely and write to the database as a compromised service account would. That work is genuinely strong. But a platform is not only its code: there is no deployment mechanism, no backup, no restore, no monitoring, and not one of the five external integrations has ever exchanged a packet with the real provider it will depend on. Certification fails on operational readiness, not on correctness.

The repository does not claim otherwise. README.md §Status and docs/SECURITY.md §Known gaps both state plainly that integration and operations work remains. This assessment confirms that self-description is accurate, quantifies what is outstanding, and adds five defects the project had not recorded.

This platform is built on an unusual and correct architectural decision: its financial guarantees live in the database, not in application code. A receipt cannot be inserted for an unverified payment because a PostgreSQL trigger refuses it. Transactions, payments, receipts, commissions and audit rows cannot be deleted or silently amended because triggers refuse that too. I attacked those rules directly with SQL, as a compromised service account or a careless DBA would, and every one of them held.

The money path is equally disciplined. No route anywhere accepts a payment status from its caller; confirmPayment takes no outcome argument and always re-asks the gateway. Ten replayed webhook deliveries produced one receipt and one commission. Ten concurrent payment initiations produced one payment row. Commission computed to the kobo at ₦1,000, ₦10,000, ₦100,000 and ₦1,000,000, and — stricter than the brief requires — will not be released until the transaction is SETTLED, meaning government has actually been paid, not merely that a gateway said so.

What fails is everything between that code and a running government service. There is no Dockerfile, no infrastructure definition, no deployment pipeline, no backup configuration and no monitoring. A restoration test — which the brief requires rather than a claim that backups exist — could not be performed because there is nothing to restore from. And the five adapters that connect this platform to Remita, the PSIRS TIN service, a KYC vendor, the vehicle registry and bank verification have only ever spoken to development mocks. The boot guard correctly refuses to start in production while any adapter is still mock, but no guard can detect a wrong field mapping against a real provider.

Separately, I found five defects the project had not recorded, two of which would cause visible harm on day one of a real deployment: every receipt would carry a QR code pointing at localhost, and the documented seeding command invites an operator to create a government administrator account with a published password in production.

Blockers

Each of these independently prevents certification. None is hidden in the recommendations below.

B-1

No deployment mechanism of any kind exists

Blocker

The repository contains no Dockerfile, no container definition, no infrastructure as code, no orchestration manifest, no service unit, and no deployment pipeline. CI builds and tests; nothing deploys. There is consequently no rollback strategy, because there is no deployment to roll back.

Evidence
A search across the repository for Dockerfile, *.tf, docker-compose*, *.service, Procfile and Kubernetes manifests returns only .github/workflows/ci.yml and .github/dependabot.yml.
Brief
§32 Production deployment checklist
B-2

No backup, no recovery procedure, and no restoration test

Blocker

Nothing in the repository configures database backups, retention, or point-in-time recovery, and no disaster recovery procedure is documented. docs/PRD-TRACEABILITY.md records RPO ≤15 min and RTO ≤2 h as targets to be agreed, not as implemented capabilities. The brief explicitly requires an actual restoration test rather than confirmation that backups exist; that test cannot be attempted.

Consequence
A storage failure loses every receipt, every transaction and the entire audit trail, permanently and with no stated recovery path.
Brief
§27 Backup and disaster recovery
B-3

No production observability — failures would be invisible

Blocker

The platform has a /health endpoint that checks database connectivity, and 62 console.* calls. There is no error tracking, no metrics endpoint, no structured logging, no uptime monitoring, no alerting, and no background-job monitoring. The reconciliation sweep logs an ABORTED run to standard output and nothing else; a reconciliation that stopped running would look exactly like one finding no exceptions.

Consequence
The brief's requirement that "critical failures must be detectable" is not met. Failed webhooks, stalled workers and unreturned refunds accumulate silently.
Brief
§28 Observability
B-4

Every external integration is unproven against its real provider

Blocker

Payment (Remita), TIN, KYC, vehicle registry and bank verification all run against development mocks. Each adapter reads its provider's response through configurable field paths and maps the provider's status vocabulary onto the platform's — and none of those mappings has been confirmed against a sandbox. The design fails closed where it can (an unrecognised KYC status becomes UNDER_REVIEW; an unmapped Remita code stays PENDING), which is the right instinct, but a mapping that is wrong rather than unrecognised is not protected by that.

Specifically unconfirmed
Remita service type ID and status code set; the PSIRS TIN format and field names; the contracted KYC vendor's status vocabulary; the vehicle registry's response shape; the bank verification endpoint.
Mitigation in place
config.ts refuses to boot in production while any adapter is mock — verified in a child process during this audit.

§3 Environment audit, §32 Deployment checklist
B-5

The seed command offers to create a production administrator with a published password

Blocker

seedDemoAgent() refuses to run when NODE_ENV=production. seedDemoUsers() has no such guard. Running npm run seed -- --demo against a production database creates five ACTIVE government accounts — including role admin at +2348000000001 — all with the password Password123.

This is not a hypothetical misuse. npm run seed is the only way to load the reference catalogue (LGAs, wards, revenue items) that production genuinely needs, so an operator setting up production will run it — and on completion it prints: "Re-run with --demo to add demonstration government users." The tool actively recommends the dangerous action, in production, with no guard.

Evidence
apps/api/src/db/seed.ts:554–582 (no isProduction check) versus apps/api/src/db/seed-agent.ts:39 (has one).
Consequence
Full administrative compromise of the platform by anyone who reads the repository.

§30 Production data audit, §21 Security audit
B-6

Public URLs default to localhost, and the production boot guard does not check them

Blocker

I booted config.ts with a fully production-shaped environment — real gateway, real TIN service, real KYC provider, real registry, real bank verification, S3 storage, 40-character secrets — and it started cleanly with:

callbackUrl : http://localhost:5173/payment/return verificationBaseUrl : http://localhost:5174/verify corsOrigins : ["http://localhost:5173","http://localhost:5174"]

VERIFICATION_BASE_URL is QR-encoded and printed onto every receipt PDF and every vehicle renewal certificate, and it forms every referee invitation link. Unset, that means: every citizen who scans their receipt to check it is genuine reaches nothing; every referee invitation is unfollowable, so no agent can ever complete clearance and the entire onboarding pipeline stops. Because receipts are immutable by design, receipts issued before anyone notices carry the broken code permanently.

PAYMENT_CALLBACK_URL unset sends the taxpayer's browser to a dead page at the moment immediately after they part with money. The payment itself still verifies by webhook, so no revenue is lost — but the citizen has no way to know that.

Evidence
apps/api/src/config.ts:130, 398; the production guard at config.ts:441–490 checks eleven other settings and not these.
Note
CORS_ORIGINS shares the defect but fails loudly and immediately, so it is self-correcting.

05

Method and evidence

I did not accept the existing test suite as evidence. I started PostgreSQL 16, applied all 15 migrations, ran the platform's own 457 tests to establish a baseline (all passed), and then wrote 39 further tests whose purpose was to break the system's stated guarantees rather than demonstrate them.

Where a guarantee is claimed to be enforced in the database, the audit bypasses the application entirely and issues SQL directly — the position of a compromised service account or a DBA at a psql prompt. A rule that only holds when you go through the service layer is not an invariant, and this distinction is what separates a real control from a convention.

Several of my early failures were my own harness being wrong about the system's contract, and each one was a control working correctly: taxpayer registration refused to proceed without explicit consentGiven and declarationAccepted; payment initiation refused to proceed without an Idempotency-Key header; the gateway simulation endpoint refused an unauthenticated caller; consumption tax refused to apply to an individual taxpayer. I corrected the harness rather than the platform in every case.

Final verification run

# tests 496 # suites 121 # pass 496 # fail 0 typecheck clean (tsc -b packages/shared apps/api && tsc --noEmit -p tsconfig.test.json) npm audit 0 vulnerabilities (production and full tree) build shared, api, agent, portal — all clean

The two audit suites are committed to this branch as apps/api/src/tests/certification-audit.test.ts and apps/api/src/tests/certification-e2e.test.ts, so the evidence behind every Pass above is reproducible rather than asserted.

Rule 6 is stronger than the brief requires

Commission does not become payable when a payment is verified. The promotion job requires transactions.status = 'SETTLED' — meaning a settlement has been recorded against a bank reference and government has actually received the money — plus the policy hold period elapsed, plus no open high-severity fraud flag. I ran the promotion job with a clock set one year forward against a verified but unsettled transaction; it released nothing. After recording a settlement, the same job released exactly one commission.

Rule 12 is enforced structurally, not by check

The offline draft queue has no payment draft type, so a payment cannot be expressed offline at all. On top of that, a runtime guard rejects any queued payload containing financial keys, and the service worker's never-cache list covers every financial path so a stale "payment successful" screen cannot be replayed. Three independent mechanisms, of which the first alone would be sufficient.

07

Financial integrity

This is the strongest part of the system and it deserves to be described precisely, because the design choice behind it is the reason the certification failure is operational rather than architectural.

The rule "no verified payment, no government receipt" is a BEFORE INSERT trigger on receipts. It checks that the referenced payment exists, is VERIFIED, carries both a verified_at timestamp and a gateway reference, belongs to the same transaction, matches the amount exactly, and that the transaction is in a state that permits issuance. A CHECK constraint separately forbids a payment row from claiming VERIFIED without recording what verified it. The practical effect is that there is no code path — API, migration, maintenance script or human at a prompt — that produces a receipt for money that did not arrive.

Duplicate protection is layered the same way. A partial unique index permits only one payment per transaction in an in-flight state, so a double-tapped Pay button cannot create two obligations even if the application logic failed. UNIQUE (gateway, event_id) on the webhook table makes a redelivery detectable at insert time. An advisory lock serialises concurrent confirmations of one payment, and verification runs at SERIALIZABLE isolation because it reads and writes the payment, the invoice and the commission ledger together.

Amount mismatch is treated as fraud, not as an error

If the gateway reports success for an amount that differs from the invoice, the platform does not issue a receipt and does not fail quietly. It moves the transaction to UNDER_REVIEW, writes a CRITICAL fraud flag recording both amounts, writes a failure audit entry, and returns an error telling the agent explicitly not to collect payment again. That is the correct handling of the case that would otherwise let a ₦100 payment discharge a ₦100,000 assessment.

08

Security and access control

Authorisation is three separate gates that are deliberately not collapsed: authenticate() confirms a live, unrevoked session; requirePermission() checks the role's permission; requireActiveAgent() checks that the agent is operationally cleared, on a registered device, running a permitted app version. A signed-in agent and a cleared agent are different things, and the platform is careful about the difference.

Two details are worth singling out. The role is read from the database on every request rather than trusted from the token, so a suspension or role change applies to sessions issued before it — I confirmed this by suspending an agent mid-session and watching the very next request return AGENT_SUSPENDED. And step-up grants are consumed, not merely checked, so one OTP authorises exactly one high-risk action and a captured token cannot approve a second payout.

Segregation of duties

The admin role can configure the platform, manage users, approve agents and change the revenue catalogue — and cannot approve a payment reversal, a refund, or a commission payout. Those require finance_officer. The auditor role holds no mutating permission at all. This is real segregation, verified by both permission inspection and a live request: an administrator calling the reversal endpoint receives 403.

The brief asks about a "KYC Officer" and a "Super Administrator". Neither exists as a distinct role; KYC review sits with revenue_officer and admin, and admin is terminal with no tier above it. Both are defensible design decisions rather than defects, but the absence of a tier above admin means there is no one who can review an administrator's own configuration changes. Worth a decision from PSIRS rather than a silent inheritance.

There is no taxpayer role, and the code documents this as a deliberate product decision: a citizen never signs in, so there is no credential to phish and no session to hijack. They receive their receipt by SMS and verify it through a public page needing no account. This is a coherent security posture — and it is exactly the posture that defect D-6 breaks, since that public page is the citizen's only recourse.

Verified during this audit

  • A JWT signed with an attacker's own key is rejected (401).
  • An alg: none unsigned token is rejected (401).
  • Session revocation takes effect on the next request, not at token expiry.
  • Passwords are bcrypt-hashed; the plaintext appears nowhere.
  • A wrong password and an unknown phone number return byte-identical responses — no user enumeration.
  • Brute-force lockout is database-backed, so it survives a multi-instance deployment.
  • Webhook signatures are verified over the raw request bytes, not the re-serialised body.
  • An unsigned or forged webhook is recorded and refused, never acted on.
  • An anonymous document request is refused; another agent cannot read a KYC document.
  • Security headers include HSTS, nosniff, frame-options: DENY, a restrictive permissions policy and no-referrer.
  • Public receipt verification returns receipt number, revenue type, amount, date and LGA — and no phone, address, name or identity hash.
09

Defects

Blockers B-1 to B-6 are above. These are the remaining findings, none of which alone prevents certification but all of which should be resolved.

D-1

Background workers assume a single instance

High

All seven workers are setInterval timers inside the API process, and the reconciliation sweep's re-entrancy guard is a module-level boolean (sweepInFlight). Behind a load balancer with N instances, N reconciliation sweeps run concurrently every six hours, each issuing a status query to Remita for every payment reference in a 48-hour window. Confirmation is idempotent so no double receipts result, but the gateway load multiplies by instance count and may hit rate limits. There is no leader election.

Location
apps/api/src/server.ts:80–160, services/reconciliation.ts:763
Fix
A PostgreSQL advisory lock around each sweep, or move the schedule out of the API process.
D-2

Migrations run on boot with no advisory lock

High

server.ts calls runMigrations() before listening, and the runner takes no lock. Two instances starting together both read the applied set and both attempt the same file; one fails and calls process.exit(1). It fails safe rather than corrupting — DDL is transactional in PostgreSQL — but a rolling deploy will crash-loop replicas until the first finishes.

Location
apps/api/src/db/migrate.ts:40
Fix
pg_advisory_lock around the run, or a separate migration step in the deploy pipeline.
D-3

Rate limiting is per-instance

Medium

The limiter keeps its buckets in a process-local Map. With N instances the effective limit is N times the configured maximum. This is documented in docs/SECURITY.md as a known gap awaiting a Redis store. The impact is bounded because account lockout — the control that actually stops credential stuffing — is database-backed.

Location
apps/api/src/middleware/security.ts:19
D-4

Vehicle renewal happy path never exercised against a real registry

Medium

The critical invariant holds — I confirmed by query that no renewal document can exist without a verified payment, and the trigger enforces it. But vehicle lookup, eligibility and authority notification have only run against the mock registry, so the full search → verify → renew → certificate → QR chain is unproven end to end. This is a specific instance of B-4.

D-5

The government portal has no automated tests

High

5,633 lines across twelve screens — where officers approve agents, review KYC documents, run reconciliation, resolve exceptions, approve payouts and execute reversals — carry no test of any kind. There is no test script in apps/portal/package.json, and the root npm test runs only the API and agent workspaces. CI typechecks and builds it; nothing exercises it.

The portal also serves the two public surfaces: receipt verification and the referee response form. A regression in either is invisible to the current suite.

Mitigating
The API tests pin the permissions each screen depends on, so a screen offering an action the API refuses is caught server-side.
D-6

Public URL defaults — see blocker B-6

Blocker

Listed here for cross-reference from the certification matrix. Full detail in §02.

D-7

Web push is unimplemented and throws

Low

providerFor('PUSH') throws by design rather than falling back to the SMS gateway — the code explains that posting a browser push subscription to an SMS vendor would fail obscurely or be silently billed. No notification template currently produces a PUSH channel, and the dispatch loop marks such a row FAILED and continues rather than stalling the queue that carries every other citizen's receipt. An honest, safely-handled gap.

D-8

No independent security or penetration testing

Medium

This audit is a source-and-behaviour assessment, not a penetration test. No network-level testing, no authenticated fuzzing, no third-party review has been performed. docs/SECURITY.md records this as outstanding. For a platform handling government revenue and citizen identity data, an independent assessment should precede go-live.

10

Operational readiness

The gap between this codebase and a running government service is the whole of the certification failure, so it is worth stating plainly what is and is not there.

What exists. A CI pipeline that builds, typechecks, migrates and tests against a real PostgreSQL service container — a genuinely good choice, since the financial guarantees are triggers and a mocked database would verify nothing. Dependabot. A /health endpoint that checks database connectivity. Graceful shutdown that drains in-flight requests before closing the pool, with a hard timeout, so a payment confirmation is never cut off mid-transaction. A production boot guard that refuses eleven classes of misconfiguration.

What does not exist. Any way to deploy the thing. Any backup. Any restore. Any alert. Any dashboard. Any error tracker. Any load test. Any staging environment described in the repository. Any rollback procedure. Any runbook for the failure modes the code carefully creates queues for — the outstanding TIN queue, the unacknowledged vehicle renewals, the unreturned refunds, the reconciliation exception queue. Those queues are well built and there is a screen that shows them; there is nothing that tells a human to go and look.

That last point is the shape of the whole problem. This platform is unusually careful about recording what it still owes — a taxpayer without their TIN, a renewal the authority never acknowledged, money a citizen has not had back. All of that honesty is only worth having if somebody is watching, and nothing in the repository arranges for anybody to be.

11

Required before production

In the order I would sequence them. Items 1 and 2 are hours of work and remove real day-one harm; the rest are the substance of the remaining programme.

  1. Guard the demo seed against production

    Add the config.isProduction check to seedDemoUsers() that seedDemoAgent() already has, and remove the "Re-run with --demo" hint when running in production. Rotate +2348000000001–05 if any environment has already been seeded. (B-5)

  2. Add the missing settings to the production boot guard

    Refuse to start if VERIFICATION_BASE_URL, PAYMENT_CALLBACK_URL or CORS_ORIGINS is unset, still on localhost, or not HTTPS. These sit alongside eleven checks that already exist. (B-6)

  3. Confirm every integration mapping against a provider sandbox

    Remita service type ID and the full status code set; the PSIRS TIN format, field paths and status vocabulary; the contracted KYC vendor's response shape; the vehicle registry; bank verification. Exercise each end to end and record the confirmed mapping. (B-4)

  4. Build the deployment path

    Container image, infrastructure definition, environment promotion, secret injection, and a documented rollback. Run migrations as an explicit pipeline step rather than on process boot. (B-1, D-2)

  5. Provision backups and perform a real restoration

    Automated backups with agreed retention, point-in-time recovery, and object-storage backup for documents. Then restore into a clean environment and verify a receipt PDF and its audit trail survive. Agree RPO and RTO with government IT and prove them. (B-2)

  6. Instrument the platform

    Error tracking, structured logging with request correlation, uptime monitoring, and alerts on the things that must never go quiet: failed webhooks, aborted reconciliation runs, growth in the exception queue, unreturned refunds, and worker liveness. (B-3)

  7. Make the workers safe for more than one instance

    Advisory locks or an external scheduler for all seven jobs, and the Redis rate-limit store already anticipated in the code comments. (D-1, D-3)

  8. Test the government portal

    At minimum the approval, reversal, reconciliation-exception and KYC-review flows, plus the two public surfaces it serves. Add it to the root test script and to CI. (D-5)

  9. Commission an independent security assessment

    Penetration testing against a deployed staging environment with real integrations configured. (D-8)

  10. Load-test the revenue path and verify the device matrix

    Establish behaviour under realistic concurrent collection load, and complete the Android, iPhone and desktop verification the PWA has not yet had.

12

Final certification

Fail

Production certification: FAIL — not production ready

Six blockers, each independently disqualifying. The application cannot yet be deployed, cannot be recovered if it fails, cannot be observed while it runs, and depends on five integrations that have never spoken to the systems they will depend on.

I want to be precise about what this verdict does and does not say, because the two halves of it point in opposite directions.

It does not say the software is untrustworthy with money. On the evidence I gathered, the opposite is true to an unusual degree. I tried to forge receipts through the API and through raw SQL, to make an agent assert a payment, to replay webhooks, to race concurrent confirmations, to rewrite a commission, to alter a paid transaction by changing its rate, to read another agent's records, to reach government endpoints as an agent, to forge a token, to inject SQL, and to delete the audit trail. Every one of those failed, most of them at the database rather than in application code, which is the difference between a control and a convention. The commission engine is exact to the kobo and refuses to pay until government has actually been paid. Offline mode cannot express a payment at all. That is a well-built revenue platform.

What it says is that a well-built application is not a production system. Two of the six blockers would cause visible harm on the first day: every citizen who scanned a receipt would find nothing, and every referee invitation would be unfollowable — which alone would halt agent onboarding entirely. Both are small code changes. The other four are programme work: deployment, backup, monitoring, and integration confirmation, none of which can be shortened by how good the code is.

The repository says the same thing about itself in README.md §Status and docs/SECURITY.md §Known gaps. That honesty is worth noting in a certification report, because the most common reason a platform like this fails in production is that nobody wrote down what was still missing. Here it was written down, and this audit largely confirms it — with five defects added that had not been recorded.
